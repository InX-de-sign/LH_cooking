How it is all wired

Azure Web App specs, every API endpoint, the full path a child's voice takes from the ESP32 to OpenAI and back — and how to swap the audio package.

Worth knowing before you change it

You are on the slow model

  • Now on eleven_turbo_v2_5 (switched 2026-08-11; was eleven_multilingual_v2, which is slower).
  • Turbo is materially lower latency than multilingual_v2, and TTS sits directly on the critical path — it is one of the legs in the latency budget.

  • Keep multilingual only if you genuinely need Cantonese/Chinese output. Note the streaming prompt path carries no language rule at all (streaming_openai.py:22-84), so the model is not currently being told to answer in Chinese anyway.
Changing the audio package

Four options, easiest first

1 · Change voice or model — no redeploy

  • These are App Settings, not code. Changing them restarts the app but ships nothing.
  • Restart drops every live WebSocket, so do it off-peak.
az webapp config appsettings set -g palop-rg -n palop-chatbot-hk --settings \
  ELEVENLABS_VOICE=rachel \
  ELEVENLABS_MODEL=eleven_turbo_v2_5

2 · Pick a different built-in voice

  • elevenlabs_voice.py ships a VOICES map of 20 aliases → voice IDs. Use the alias, not the ID.
  • Female: rachel, sarah (current), sarah_mature, domi, emily, elli, dorothy
  • Male: drew, clyde, paul, dave, fin, antoni, thomas, charlie, george, callum, patrick, harry, liam
  • For a voice not in the map, add the alias → ID pair to VOICES and redeploy.

3 · Switch provider to Google gTTS — free, no key

  • TTS_PROVIDER=google makes zoo_api.py:51 reuse OptimizedVoiceComponent for both STT and TTS.
  • No ElevenLabs key needed, no per-character cost.
  • Quality is noticeably worse for a children's companion, and both STT and TTS then share one 2-worker thread pool — a real bottleneck under concurrency.
az webapp config appsettings set -g palop-rg -n palop-chatbot-hk --settings TTS_PROVIDER=google

4 · Add a new provider (Azure Speech, Cartesia, PlayHT…)

  • The contract is one method. Anything implementing it drops straight in:
class MyVoice:
    async def create_audio_response_async(self, text: str) -> bytes | None:
        """Return MP3 bytes. The caller decodes to 16 kHz mono WAV itself."""
  • Register it beside the existing branch in zoo_api.py:42-51.
  • Return MP3 — audio_receiver.py:_mp3_to_esp32_wav handles the rest via miniaudio.
  • If your provider returns WAV or PCM directly, skip the decode entirely and save a step.
  • Azure Speech would be the natural fit — same cloud, same region, so it removes one cross-continent hop from the latency chain.

Limits you are living with on F1

  • 5 concurrent WebSockets per instance. Linux Free is capped at 5; every other tier is ~50,000. Two ESP32 units plus a browser tab is already most of your budget.
  • No Always On. After 20 minutes with no incoming HTTP request, the app unloads and every socket dies. An idle WebSocket does not count as a request.
  • 60 CPU-minutes/day and 1 GB storage on Free.
  • Fix is one command, no redeploy: az appservice plan update -g palop-rg -n palop-plan --sku B1

Platform behaviours that apply at every tier

  • 4-minute idle timeout at the Azure Load Balancer (~240 s on Linux), and it is not configurable. Any socket silent for that long is torn down. The ESP32 pings every 15 s so it stays alive — but the server does not handle those pings, they hit the unknown-message branch.
  • Every app-setting change restarts the app and drops all live sockets. There is no zero-downtime path for stateful connections.
  • Code runs from /tmp/<uid>, not /home/site/wwwroot, when build automation is on. Only /home persists across restarts.

End to end

How information travels

One complete turn: child presses the button, hears an answer.

01
ESP32 audio unit · on site

Capture

  • Button press triggers a fixed 5-second I2S recording — 16 kHz, mono, 16-bit = 160,000 bytes into PSRAM.
  • One blocking i2s_read; no voice-activity detection, no early stop.
  • An 8× software gain is applied, then a 44-byte RIFF header is prepended.
02
ESP32 → Azure · WSS 443

Uplink

  • The 160,044-byte WAV is split into 20 chunks of 8 KB.
  • Each chunk is base64-encoded and wrapped in JSON, sent as a WebSocket text frame — never binary.
  • That inflates 160 KB to about 213 KB on the wire, a 33% overhead.
  • Fixed pacing: 10 ms between chunks, 50 ms before the audio_complete marker.
03
Azure App Service · Switzerland North

Ingress

  • TLS terminates at nginx, which proxies to gunicorn → uvicorn → FastAPI.
  • Chunks are base64-decoded and appended to a per-client deque(maxlen=100).
  • Nothing happens until the COMPLETE marker arrives. The whole 5 seconds must land before transcription starts — this is a batch pipeline, not a streaming one.
  • Chunks are reassembled into a single WAV with a fresh RIFF header.
04
Azure → Google · HTTP

Speech to text

  • The WAV is written to a temp file on disk, re-read, and FLAC-encoded at maximum compression.
  • Sent to Google's free speech endpoint. Up to three sequential attempts across languages — with English tried last.
  • Runs on a 2-worker thread pool; no per-request timeout is set.
  • Returns a single finished transcript string. No partial results.
05
In process

Context assembly

  • SQLite lookups against zoo.db (8 rows, no indexes) and memory.db.
  • Despite the "RAG" naming there is no vector store — retrieval is a LIKE '%name%' scan plus hardcoded dictionaries. It costs milliseconds.
  • If the vision service posted a detection recently, that animal is added as context.
  • Most of the assembled context is then discarded — the streaming prompt builder reads only the detected animal and a truncated database excerpt. Conversation history is loaded and never used, so the voice path has no memory between turns.
06
Azure → HKUST gateway · HTTPS

Generation

  • gpt-4o-mini via hkust.azure-api.net, max_tokens=50, streamed as server-sent events.
  • The client is synchronous, so the event loop is blocked for the entire generation — not just until the first token.
  • No timeout is configured, so the SDK default of 600 seconds applies.
07
Azure → ElevenLabs · HTTPS

Speech synthesis

  • The text stream is cut at sentence boundaries — first phrase at 25 characters, later ones at 60 — so synthesis can start before the model finishes.
  • Each phrase is sent to ElevenLabs and comes back as MP3.
  • MP3 → 16 kHz mono WAV is done in-process by miniaudio, no ffmpeg subprocess.
  • Up to 3 phrases synthesise concurrently; they are always sent in order.
08
Azure → ESP32 · WSS 443

Downlink and playback

  • Per phrase: an audio_start JSON frame, then raw WAV in 4 KB binary frames, then audio_complete.
  • The ESP32 queues up to 5 streams and plays them FIFO, keyed on the phrase field.
  • Playback begins once about 380 ms of audio is buffered, then feeds the I2S DAC 1 KB at a time.
  • Audio reaches the speaker through an 8-buffer DMA ring.
Known issues on this path

Three things that are wrong today

  • The sentence-streaming optimisation cannot take effect while the OpenAI client is synchronous — the blocked event loop prevents any synthesis task from running until generation completes.
  • The firmware waits a full phrase-length plus 2 seconds of silence after every phrase before advancing its queue. With multi-phrase streaming that becomes a gap inside every sentence.
  • Conversation memory is written to ephemeral storage. memory.db lives outside /home, so it is wiped on every restart — and app-setting changes restart the app.
