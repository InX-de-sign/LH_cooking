Offline reference

Visit onboarding and conversation memory

PAL_OP personalizes one park visit without creating a cross-visit user account. The guide collects a small visit profile before normal conversation, then uses visit, episode, turn, and fact-ledger state to build each model request.

Design decision

All current memory is local, visit-scoped SQLite state

There is no PostgreSQL, Redis, external profile store, account, or tour mode. Every visitor starts in a free visit. The profile is attached to one visit and is not used to identify or personalize a later visitor.

The model

Profile, visit, episode, and turn

VISIT PROFILE     name, exact age, derived audience mode, interests, language
       |
       +-- VISIT      one park trip for one device/client identifier
       |     |
       |     +-- EPISODE   coherent discussion of one animal, exhibit, or park subject
       |     |     |
       |     |     +-- TURN  one visitor utterance and one guide response
       |     |
       |     +-- DELIVERED FACTS  facts already used during this visit

The profile changes how the guide explains. Episodes and facts record what has already been discussed. The system stores the complete visit history but retrieves only the small, relevant subset needed by the next prompt.

Before normal chat

Onboarding flow

On a browser connection or ESP32 audio registration, the application starts or resumes the active visit and asks the next unanswered profile question. These questions are deterministic responses from the application; they do not call GPT or retrieve park facts.

1
Name

Ask for a name

The stored value is used only within the current visit.

2
Exact age

Ask "How old are you?"

An age from 1 to 120 is required as a number. The code derives an internal audience mode: early_child (1-5), child (6-8), older_child (9-12), teen (13-17), or adult (18+).

3
Interests

Ask what they want to see

This is free text, for example "marine animals" or "rides".

4
Reply language

Ask for Mandarin or English

The answer sets the visit language to zh or en. Once chosen, it takes precedence over automatic language detection for the rest of the visit.

5
Guide conversation

Enable normal questions

Only after step 4 is complete can the request reach subject resolution, fact retrieval, and GPT.

There is deliberately no visit_mode or tour-route field. The current product behavior is always a free visit.

Persistence

What is in memory.db

ConversationStore opens SQLite at MEMORY_DB_PATH, or memory.db when that environment variable is not set. It applies a migration at startup so databases created before onboarding gain the new visit profile columns automatically.

TableScopePurpose
visitsOne park tripClient identifier, timestamps, language, profile values, onboarding state, and total turns.
episodesWithin a visitCurrent subject identity, how it was chosen (camera, named, carried), timestamps, turn count, and facets already discussed.
turnsWithin an episode/visitVisitor text, guide response, facet, language, source, and the retrieved fact IDs.
delivered_factsWithin a visitFact IDs already supplied to the guide so a repeated "tell me more" can retrieve fresh material.

The 30-minute boundary starts a new visit; it does not delete rows

After SESSION_IDLE_SECONDS (30 minutes by default), the same device/client ID receives a fresh visit and must complete onboarding again. Existing rows remain in the SQLite file until an operator removes the file or a future retention job deletes them. Where Docker stores the file determines whether it survives a container restart: the production compose configuration mounts /app/data/memory.db in a named volume.

Episode memory

How an animal discussion stays coherent

An episode is the active discussion of a subject such as a Red Panda, an exhibit, or a park-level topic. It preserves the subject and facets already covered while the visitor continues asking related questions. The active episode is reused for the same subject within eight minutes by default.

Visitor wordingResolutionWhy episode state matters
"What do they eat?"Anaphoric marker - use the active episode subject.The camera can drift without changing what "they" means.
"What animal is this?"Demonstrative marker - prefer the current camera detection.The visitor is pointing at the animal in front of them, not necessarily the previous subject.
"Tell me more"Follow-up marker - retain the episode subject.The delivered-fact ledger excludes facts already used in the visit.
"Tell me about capybaras"Explicitly named subject - start or switch to its episode.A named animal outranks the camera label.

The current implementation carries the active episode and lists prior subjects in the visit summary. It does not yet implement semantic retrieval of arbitrary older episodes such as "compare this with the animal from an hour ago"; that is a future enhancement, not a behavior this document promises today.

Per-request context

What reaches GPT on a normal turn

GPT API calls are stateless, so the application builds a compact prompt context every time. It does not send all rows from the visit database. 

[VISITOR]  Name, exact age with derived audience mode, interests.
[VISIT]    Selected language, visit duration, question count, earlier subjects.
[NOW]      Resolved subject, source of resolution, zone, active episode summary, facet.
[RECENT]   Up to 3 previous exchanges, oldest first; guide replies are clipped to 160 characters.
[FACTS]    Up to 4 retrieved, grounded facts not already delivered this visit.
[QUESTION] The incoming visitor utterance.

The model uses this context to write the answer. The application remains responsible for subject choice, local fact retrieval, language choice, and profile/episode persistence.

Operational reference

Relevant implementation files

  • chatbot/conversation_state.py - SQLite schema, migration, visit profile, onboarding state, episodes, turns, and fact ledger.
  • chatbot/context_builder.py - subject resolution and rendering of the five prompt layers.
  • chatbot/zoo_main.py - gates both standard and streaming model paths behind onboarding.
  • chatbot/zoo_api.py - starts onboarding for browser WebSocket connections and returns UI state.
  • chatbot/audio_receiver.py - speaks the first profile question to registered ESP32 audio clients.
  • chatbot/static/zoo_index.html - browser onboarding presentation and quick-question gating.
