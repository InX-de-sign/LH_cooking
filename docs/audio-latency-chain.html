Audio pipeline · latency audit

Where the seconds go

A child presses the button and waits somewhere between seven and ten seconds to hear a reply. This traces every millisecond of that path — mic to speaker — against the code that causes it.

Finding 01 · blocks everything downstream

The streaming client is synchronous, so nothing overlaps

chatbot/streaming_openai.py:5 imports the sync AzureOpenAI. A repo-wide search for AsyncAzureOpenAI returns nothing. Line 97 calls client.chat.completions.create(..., stream=True) with no await, and line 112 drains the response with a plain for chunk in stream:. Between lines 97 and 118 there is not a single await.

The event loop is therefore frozen for the entire generation, not merely time-to-first-token. This nullifies the sentence-boundary TTS streaming committed in d0bd442: asyncio.create_task() at audio_receiver.py:574 only schedules the synthesis, and nothing can run it until the blocking loop returns. The measured 1.73s saving came from a mock that used a genuine async generator — against the real client the overlap is approximately zero.

The fix is small. AsyncAzureOpenAI + async for is a drop-in swap that the SDK already ships, and it needs no change to produce()/consume(). Note the correct pattern already exists in this codebase — enhanced_rag_openai.py:566–593 wraps its call in run_in_executor. It is only on the non-streaming path, which the voice loop never takes.

Finding 02 · gets worse with multi-phrase audio

The firmware waits a full phrase-length of dead air after every phrase

zoo_esp32/audio_tailscale copy.ino:759 computes drainDelay = (samples * 1000 / SAMPLE_RATE) + 2000 — the phrase's own duration, plus two seconds — and refuses to advance the queue until it elapses. But i2s_write(..., portMAX_DELAY) on line 748 has already blocked until the DMA accepted every byte. The only genuine residue is the DMA ring itself: dma_buf_count = 8 × dma_buf_len = 1024 (lines 847–848) ≈ 512 ms.

So each phrase costs its own duration + 2.0s of silence before the next one starts. A 3-second phrase produces a 5-second gap. Under the single-utterance design that was one trailing pause nobody noticed. With sentence-boundary streaming it becomes a gap in the middle of every sentence — five phrases means five gaps. Until this line is fixed, d0bd442 makes the experience on real hardware worse, not better.

Replacing the formula with a fixed ~600 ms recovers phrase duration + 1.4s per phrase. This is the single largest avoidable constant anywhere in the chain.

Mic to speaker

The chain, stage by stage

Every citation below was opened and verified by a second pass; line numbers are exact.

Stage01

Capture — ESP32 microphone

5.00s fixed

A falling edge on BUTTON_PIN (ino:928) triggers record_audio(). It allocates 160,000 bytes in PSRAM (ino:581) — exactly RECORD_DURATION_SEC(5) × 16000 Hz × 2 bytes (ino:273–276) — then makes one blocking call: i2s_read(..., AUDIO_BUFFER_SIZE, portMAX_DELAY) at ino:589. There is no VAD, no silence detection, no early stop.

Nothing services the WebSocket during this window — webSocket.loop() appears only at ino:916. Inbound frames pile up in LwIP for the whole 5 seconds.

Stale-audio defect: the RX driver is installed at ino:835 and never stopped or flushed — a search for i2s_zero_dma_buffer/i2s_start/i2s_stop returns zero hits. Every recording therefore begins with audio captured before the press and ends short by the same amount. One-line fix: flush before the read.

Stage02

Uplink — base64 JSON over WebSocket

0.25s fixed +33% wire

The buffer is copied again into a 160,044-byte send buffer with a RIFF header (ino:609–616), split into 20 chunks of 8192 bytes (ino:620–621), each base64-encoded (ino:630), wrapped in JSON (ino:633) and sent as a text frame (ino:652).

Base64 inflates 160,044 bytes to 213,420 characters. sendBIN is never called anywhere in the firmware, and the server has no binary branch — it decodes message["audio"] at audio_receiver.py:253 — so cutting that third off the wire needs both ends changed.

Fixed pacing: delay(10) × 20 chunks = 200 ms (ino:661), plus delay(50) before audio_complete (ino:665). Both are defensive; TCP already guarantees ordering. Replacing the first with webSocket.loop() would also fix the RX starvation above.

Stage03

Ingress — the batch barrier

0–50ms poll

Chunks land in a per-client deque(maxlen=100) (audio_receiver.py:258). _process_audio_queue polls it with await asyncio.sleep(0.05) when empty (line 307) and only enters the STT block inside if item == "COMPLETE": (line 324).

The docstring at lines 293–294 is false. It claims "starts STT as soon as first chunk arrives"; the first-chunk branch (313–322) only sends a status frame and does no STT. Nothing is transcribed until all 5 seconds have arrived.

The maxlen=100 deque is silent lossy backpressure — overflow evicts from the left with no log, and the consumer blocks for seconds inside the response pipeline (line 370). A second utterance can push away the start of the first.

Stage04

Speech to text — up to three sequential HTTP calls

0.5–1.8s

Chunks are reassembled into a WAV (audio_receiver.py:686), written to a temp file on disk (optimized_voice.py:237), re-read, and handed to speech_recognition's recognize_google — the free Chromium endpoint, over plain HTTP, with a shared hardcoded key.

Each attempt FLAC-encodes the clip at --best: measured 0.140s / 0.148s / 0.230s on this machine. The code then tries up to three languages sequentially (optimized_voice.py:257) with en-US last, so an English speaker routinely pays three encodes and three round trips.

adjust_for_ambient_noise(source, duration=0.3) at optimized_voice.py:251 discards 0.256s from the start of every utterance — and the threshold it computes is only consulted by listen(), which this path never calls. It is pure accuracy loss. Separately, operation_timeout is never set (line 93), so a stalled request pins one of only two executor threads indefinitely; the wait_for(timeout=30.0) at audio_receiver.py:718 gives the illusion of a bound but cannot reclaim the thread.

Stage05

Language model — blocking, and mostly ignored context

blocks loop

Retrieval runs first and synchronously: zoo_main.py:146–175 opens sqlite connections (lines 245, 278, 301) on the event-loop thread. There is no vector store despite the RAG naming — retrieval is LIKE '%name%' over an 8-row, unindexed table, so it costs milliseconds. Only its blocking-ness is a problem, not its ordering.

Then the sync client call described in Finding 01. With openai==1.101.0, no timeout override means the SDK default of 600 seconds applies — a hung gateway blocks every other websocket client for ten minutes.

Work paid for and discarded: _build_short_prompt (streaming_openai.py:127–152) reads only detected_animal and local_database. So cv_instruction, conversation_history, conversation_responses and user_context are all assembled and silently dropped — the voice path has no conversational memory even though a DB query loaded it. The streaming prompts also carry no language rule, unlike the non-streaming ones (enhanced_rag_openai.py:70–74), so a Cantonese question gets no instruction to answer in Cantonese.

Stage06

Text to speech and downlink

0.17s / phrase

Each phrase goes to ElevenLabs, returns MP3, and is decoded to 16 kHz mono WAV by pydub in an executor (audio_receiver.py:492 — correctly off the event loop). Framing per phrase: audio_start, a fixed sleep(0.1) (line 517), 4096-byte binary chunks each followed by sleep(0.001) (line 521), then sleep(0.05) before audio_complete (line 523).

The 0.1s exists so the ESP32 can allocate a queue slot — but the firmware already has an auto-allocate fallback at ino:537–544, so it is redundant padding. Synthesis concurrency is capped at MAX_CONCURRENT_TTS = 3 (line 421) against the device's 5-slot queue.

Stage07

Playback — pre-roll and the drain stall

+2s / phrase

Playback will not begin until stream->size > 8192 (ino:559). Because the server sends 4096-byte chunks, that strict > only passes on the third chunk — 383 ms of audio buffered where >= would have started at 255 ms.

Then the drain stall of Finding 02. Also note i2s_write(..., portMAX_DELAY) at ino:748 blocks the main loop for up to 64 ms at a time, so webSocket.loop() is serviced only every 32–64 ms during playback — throttling the very downlink that is feeding it.

Not latency, but found on the way

Correctness issues

A client whose first message is settings is permanently mute

audio_receiver.py:147–160 stores settings, acks, then calls _handle_audio_stream without the asyncio.create_task(self._process_audio_queue(...)) that both the register branch (133–135) and the audio_chunk branch (186–188) perform. The deque fills, the COMPLETE sentinel lands in a queue nobody ever pops, and the client is transcribed never — with no error anywhere.

Sample-rate agreement is coincidence, not design

The firmware reports its rate inside the register message (ino:434–436), and the register handler never reads it. The audio_chunk handler ignores the rate on chunk 0 too. So client_settings is empty for every ESP32 client and _combine_to_proper_wav falls back to a hardcoded 16000 (audio_receiver.py:654) — which happens to match SAMPLE_RATE in the firmware.

Change either constant and the server stamps a wrong header, Google receives pitch-shifted audio, and STT returns garbage with no error. Worse: the three other places that populate client_settings (lines 149, 170, 278) all default to 44100.

The web_ client-id prefix is silently destroyed

zoo_api.py:212 slices [-10:] across the whole f-string rather than the numeric part. Verified by execution: 'web_-1474576251381098940_1234' becomes '98940_1234'. Because recent_detections is keyed on the mapped id, the CV-context branch at zoo_api.py:239 is unreachable in practice for every web client.

Dead code that other code depends on

_play_waiting_audio (audio_receiver.py:792–848) has no caller — yet _cancel_waiting_audio and the cancels at 375–377, 597 and 613 all assume it runs. Since waiting_audio_tasks is therefore always empty, every one of those cancels is a no-op.

Also unreferenced: _generate_and_queue_mp3, _stream_single_phrase_mp3, and by extension ESP32TTSStreamer entirely. self.tts_connections and self.stream_func are assigned in __init__ and never read.

Voice recordings travel over plain HTTP

The recognize_google endpoint is http://, not HTTPS, authenticated with a shared hardcoded Chromium key. Children's voice recordings traverse the network unencrypted, and Google can revoke that key without notice — the failure mode would be a silent, permanent “say again” loop. The advertised offline fallback cannot fire: pocketsphinx is not in requirements.txt, not installed in the Dockerfile, and not importable.

A held button re-triggers recording indefinitely

The PSRAM headroom guard at ino:948–951 returns before lastButtonState is updated at ino:978. With the button held, lastButtonState stays HIGH, so the HIGH→LOW edge re-fires every iteration — a ~50 ms spin, or ~150 ms when the conditional delay(100) at 942 also runs.
