The public host is Tencent Lighthouse in Hong Kong. Caddy is the only public container: it listens on ports 80 and 443, issues TLS certificates, routes /vision/* to YOLO, and sends all other requests to the chatbot. Azure OpenAI remains an external model provider.

The chatbot uses the internal application network for YOLO and MediaMTX plus an outbound egress network for Azure DNS and HTTPS. This separation is intentional: the chatbot must reach Azure, but neither chatbot nor YOLO needs a public port.

Practical rule: VS Code terminal and standalone Windows PowerShell are both fine. The important distinction is the prompt. Once ssh succeeds and the prompt begins with ubuntu@, all following commands are Linux commands on the server.

Accessing the Ubuntu host

Run in Windows PowerShell

Normal SSH access

ssh -i "$HOME\.ssh\pal-op-lighthouse" ubuntu@YOUR_LIGHTHOUSE_IP

Use a VS Code integrated PowerShell terminal when editing code because it can also run scp from the repository. A standalone PowerShell terminal works equally well.

Run in Windows PowerShell

Copy one local file

scp -i "$HOME\.ssh\pal-op-lighthouse" "F:\_VScode2\PAL_OP\docker-compose.lighthouse.yml" ubuntu@YOUR_LIGHTHOUSE_IP:~/pal-op/

Use scp for a focused emergency deployment. Prefer git pull on the server for a normal published release.

Run after SSH connects

cd ~/pal-op

The expected directory is /home/ubuntu/pal-op. Linux uses forward slashes and ~/pal-op, not a Windows drive letter.

Console fallback

When SSH fails

Open the instance in the Tencent Lighthouse console and choose the browser login/terminal option. Use it to inspect firewall, network, or SSH setup, then return to normal SSH access when possible.

One-time server setup

  1. Create an Ubuntu Lighthouse instance with enough CPU/RAM for CPU inference. GPU is not required by the current YOLO deployment.
  2. Configure a DNS A record for the chosen domain to the Lighthouse public IPv4 address. Caddy needs DNS to point at the host before it can obtain a TLS certificate.
  3. Allow inbound TCP ports 22, 80, and 443 in the Lighthouse firewall. Keep inference and database ports private.
  4. Install Docker and Docker Compose, then clone the repository into ~/pal-op.
  5. Create .env.lighthouse from .env.lighthouse.example, populate it only on the server, and never commit it.

Environment file and line endings

Linux shell files can fail when copied from Windows with CRLF line endings. A broken .env.lighthouse often causes confusing command not found errors when it is loaded.

Run after SSH connects 
cd ~/pal-op
cp .env.lighthouse .env.lighthouse.before-line-ending-fix
sed -i 's/\r$//' .env.lighthouse
set -a; . ./.env.lighthouse; set +a
test -n "$OPENAI_API_KEY" && echo "OPENAI_API_KEY=set" || echo "OPENAI_API_KEY=MISSING"

The sed command removes only carriage-return characters; it does not reveal or change a secret value.

cd ~/pal-op

Azure OpenAI checks

Check Azure from both the host and container when diagnosing a connectivity issue. A host can resolve an address while a container cannot.

Run after SSH connects 
cd ~/pal-op
set -a; . ./.env.lighthouse; set +a
url="${AZURE_OPENAI_ENDPOINT%/}/openai/deployments/${AZURE_DEPLOYMENT_NAME}/chat/completions?api-version=${AZURE_OPENAI_API_VERSION}"
curl -sS -o /dev/null -w 'api-key=%{http_code}\n' --connect-timeout 10 --max-time 30 -H "Content-Type: application/json" -H "api-key: $OPENAI_API_KEY" --data '{"messages":[{"role":"user","content":"Reply only with OK"}],"max_tokens":2}' "$url"
Run on the Ubuntu host; Docker executes inside chatbot 
docker compose --env-file .env.lighthouse -f docker-compose.lighthouse.yml exec chatbot python -c 'import socket; socket.getaddrinfo("hkust.azure-api.net", 443); print("AZURE_DNS_OK")'
docker compose --env-file .env.lighthouse -f docker-compose.lighthouse.yml exec chatbot python -c 'from config import load_azure_openai_config; from openai import AzureOpenAI; c=load_azure_openai_config(); r=AzureOpenAI(api_key=c.api_key, api_version=c.api_version, azure_endpoint=c.azure_endpoint, timeout=30, max_retries=0).chat.completions.create(model=c.deployment_name, messages=[{"role":"user","content":"Reply only with OK"}], max_tokens=2); print("AZURE_COMPLETION_OK" if r.choices else "AZURE_COMPLETION_EMPTY")'

api-key=200 and AZURE_COMPLETION_OK mean endpoint, deployment, credentials, DNS, container networking, and model access are working. Do not switch headers unless the gateway owner explicitly requires it.

Operations checklist

  1. Before update: confirm git status locally; never overwrite .env.lighthouse with a repository file.
  2. Deploy: update source, rebuild affected service, and check docker compose ... ps.
  3. Validate: check public /health, chatbot logs, then one browser or ESP32 interaction.
  4. After infrastructure changes: verify host and container Azure access separately.
  5. Before major upgrades: back up the chatbot_data Docker volume, which contains SQLite memory.
  6. Keep public exposure minimal: only SSH, HTTP, and HTTPS. Leave chatbot, YOLO, MediaMTX, and databases private unless hardware requires otherwise.
