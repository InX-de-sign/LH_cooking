Reproducible

The commands, in order

Every one of these was actually run. Re-runnable from scratch on any subscription without a region policy.

Step01

Pick a subscription that allows your region

az account set --subscription 1605ab78-e2a6-4a7d-8198-7cffb175ff48

# check for a region allow-list policy BEFORE provisioning
az policy assignment list \
  --query "[?displayName=='Allowed resource deployment regions'].parameters.listOfAllowedLocations.value" -o json

This check is not optional — see the region traps. An empty result means no restriction. On Azure for Students it returns five European/African regions and no Asian region at all.

Step02

Resource group, plan, web app

az group create -n palop-rg -l switzerlandnorth

az appservice plan create -g palop-rg -n palop-plan --is-linux --sku F1 -l switzerlandnorth

az webapp create -g palop-rg -p palop-plan -n palop-chatbot-hk --runtime "PYTHON:3.12"

# ALWAYS check this - a plan can create fine while the app lands stopped
az webapp show -g palop-rg -n palop-chatbot-hk --query state

App names are globally unique. Check first with the checknameavailability ARM endpoint rather than discovering it on failure.

Expect intermittent ResourceNotFound from az webapp show and config set for a minute or two after creation — ARM propagation lag, not a real failure. Retry rather than recreating.

Step03

Runtime, startup command, WebSockets

az webapp config set -g palop-rg -n palop-chatbot-hk \
  --linux-fx-version "PYTHON|3.12" \
  --startup-file "gunicorn -w 2 -k uvicorn.workers.UvicornWorker \
                  -b 0.0.0.0:8000 --timeout 600 zoo_api:app" \
  --web-sockets-enabled true

Three things here are load-bearing. az webapp create returned an empty linuxFxVersion despite the --runtime flag, so it is set again explicitly. --timeout 600 is included because Microsoft's own documented command omits it, which silently drops you to Gunicorn's 30-second default. And --web-sockets-enabled is set rather than assumed: Microsoft documents no default value for it anywhere.

Step04

App settings — secrets and platform flags

az webapp config appsettings set -g palop-rg -n palop-chatbot-hk --settings \
  AZURE_OPENAI_ENDPOINT=... AZURE_OPENAI_API_VERSION=... AZURE_DEPLOYMENT_NAME=... \
  OPENAI_API_KEY=... ELEVENLABS_API_KEY=... ELEVENLABS_VOICE=... \
  TTS_PROVIDER=elevenlabs \
  SCM_DO_BUILD_DURING_DEPLOYMENT=1 \
  WEBSITES_CONTAINER_STOP_TIME_LIMIT=120 \
  PYTHONUNBUFFERED=1

SCM_DO_BUILD_DURING_DEPLOYMENT=1 is what makes Oryx run pip install -r requirements.txt at all — without it, zip deploy ships your code with no dependencies. WEBSITES_CONTAINER_STOP_TIME_LIMIT=120 raises the graceful-shutdown window from its 5-second default, which is far too short to close WebSockets cleanly on a restart.

Secrets go here, never into the deployment package — .env is deliberately excluded from the zip in the next step.

Step05

Deploy

# zip the CONTENTS of chatbot/ — requirements.txt must be at the package root,
# excluding .env, __pycache__, logs/, memory.db
az webapp deploy -g palop-rg -n palop-chatbot-hk \
  --src-path palop-deploy.zip --type zip

Oryx detects requirements.txt only in the package root, which is why the zip contains the contents of chatbot/ rather than the repository root. Expect "status": "RuntimeSuccessful".

Step06

Verify, and stream logs if it fails

curl -s https://palop-chatbot-hk.azurewebsites.net/health

az webapp log tail -g palop-rg -n palop-chatbot-hk

Required before it would run at all

Code changes the platform forced

Trap 01 · would crash on the TTS hot path

No ffmpeg — and the obvious workaround does not work

pydub.AudioSegment.from_mp3() shells out to an ffmpeg binary. The App Service Python image ships neither ffmpeg nor ffprobe, and there is no root to apt-get them.

The usual fix — pip install imageio-ffmpeg and set AudioSegment.converter — still fails, because from_mp3() spawns ffprobe first to sniff the format, and imageio-ffmpeg ships ffmpeg only. Worse, the widely-copied AudioSegment.ffprobe = "..." line is a silent no-op: pydub has no such attribute, so Python just creates an unused one and the decode still raises.

Fix applied: replaced the decode with miniaudio, which does MP3 decode, stereo→mono downmix and the 16 kHz resample in one in-process C call. A 200 KB wheel instead of an 80 MB binary, and no subprocess per phrase. 

decoded = miniaudio.decode(mp3_audio,
                           output_format=miniaudio.SampleFormat.SIGNED16,
                           nchannels=1, sample_rate=16000)

Verified locally against a real 21,696-byte MP3 → 16 kHz mono s16, 2.71 s, valid RIFF/WAVE header matching the ESP32 I2S contract.

Trap 02 · would have failed silently

One import killed speech recognition entirely

speech_recognition and pyaudio shared a try block. PyAudio needs portaudio19-dev, which cannot be installed on App Service — so its ImportError set HAS_SPEECH_RECOGNITION = False.

The failure mode is the dangerous kind: the service boots, passes health checks, accepts WebSockets, and simply never transcribes anything. gtts was gated the same way through pygame.mixer.init().

Fix applied: split the imports so pygame and pyaudio are independently optional. Neither is needed server-side — one is local playback, the other live microphone capture, and this server does neither.

Trap 03 · startup crash loop

A relative path that only resolves on your laptop

zoo_api.py checked os.path.exists("zoo.db") — relative to the working directory. Under App Service build automation the app is served from /tmp/<uid>, not the code directory, so that check reports missing and the next line imports create_zoo_database — a module that does not exist anywhere in this repo. A false negative becomes ModuleNotFoundError in a restart loop.

Fix applied: resolve against __file__ and log rather than import. Also uvicorn.run(port=8000) now reads $PORT.

Trap 04 · blocked provisioning outright

Azure for Students bans every Asian region

The first attempt targeted the Students subscription. Creating the plan failed with RequestDisallowedByAzure. Its policy allows only: 

austriaeast · switzerlandnorth · southafricanorth
germanywestcentral · italynorth

No Asian region at all. For a product serving Hong Kong Ocean Park that is a real cost — measured at 3.01 s to first response from Switzerland versus 1.63 s from East Asia, so roughly 1.4 s handed back. The app lives on Students for account-ownership reasons, so this is accepted for now. Two ways out: raise an Azure support request to add eastasia to the Students allow-list, or move to an Asian region on a different subscription before real users.

Trap 05 · app created, then silently stopped

Free-tier capacity is per REGION, and B1 quota is zero

The first Students attempt used germanywestcentral. The resource group and the F1 plan both created cleanly — and then the web app sat in state QuotaExceeded, refusing every request with 403 · This web app is stopped. Every usage counter read 0 against a limit of -1, so it was not consumption; that region is simply out of free-tier capacity.

Upgrading was not an escape either — az appservice plan update --sku B1 returned Current Limit (B1 VMs): 0. Azure for Students carries no Basic quota at all.

How it was diagnosed: create a throwaway F1 app in a different allowed region and compare. The probe in switzerlandnorth came up Running, proving the block was regional rather than subscription-wide. Rebuilding there worked. 

# a plan creating successfully proves nothing - always check the APP state
az webapp show -g palop-rg -n <app> --query state
# "Running" = good.  "QuotaExceeded" = pick another region.
